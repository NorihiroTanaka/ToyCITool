# fix-with-plan

修正作業を「計画 → 確認 → 実装」の流れで進めるスキル。
問題を分析して修正計画を立案し、サブエージェントに実装を委譲する。

## なぜこの流れが重要か

修正計画を先に出力することで：
- 修正の方向性をユーザーが事前に確認できる
- 見当違いな修正を実施してしまうリスクを減らせる
- 影響範囲と注意点を事前に把握できる
- サブエージェントへの指示が明確になり、実装品質が上がる

---

## Step 1: 問題の分析

ユーザーの依頼内容をもとに、関連コードを調査する。

**調査する情報**:
- エラーメッセージ・スタックトレース（ユーザーが提供している場合）
- 問題が発生しているファイル・関数・クラス
- 関連するテストコード
- 最近の変更（git log / git diff で確認）

```bash
# 例: 関連ファイルを特定する
# Glob, Grep, Read を使って問題箇所を特定する
```

分析の観点:
- **症状**: 何が起きているか（エラー内容・誤った出力・テスト失敗）
- **根本原因**: なぜ起きているか（ロジックの誤り・型の不一致・副作用・競合）
- **影響範囲**: どのファイル・関数を変更する必要があるか
- **リスク**: 修正によって壊れる可能性がある箇所

---

## Step 2: 修正計画の立案と出力

分析結果をもとに修正計画を立案し、ユーザーに提示する。
ユーザーが計画を見て方向性を確認できるよう、**コードを書く前に必ず計画を出力する**。

### 修正計画の出力フォーマット

以下のテンプレートで出力する:

```
## 修正計画

### 問題の概要
<何が起きているか、ユーザーが報告した症状を簡潔に説明>

### 根本原因
<なぜこの問題が発生しているか。コードの該当箇所（ファイル名:行番号）とともに説明>

### 修正方針
<どのようなアプローチで修正するか。複数の選択肢がある場合はここで提示し、どれを採用するか説明>

### 修正ステップ
1. **[ファイル名]** - <何を変更するか>
   - 変更内容: <具体的な変更の説明>
   - 理由: <なぜこの変更が必要か>

2. **[ファイル名]** - <何を変更するか>
   ...

### 影響範囲
- 変更するファイル: <一覧>
- 既存テストへの影響: <テストが壊れる可能性があるか>
- 動作への影響: <外部から見た振る舞いが変わるか>

### 確認方法
<修正後にどう動作を確認するか（実行コマンド・テスト・手動確認など）>
```

**計画の粒度の目安**:
- 変更するファイルと変更箇所が明確になっている
- 「なぜその変更が必要か」が説明されている
- 修正後の確認方法が具体的

---

## Step 3: ユーザーへの確認

計画を出力したら、実装に進む前にユーザーに確認を求める。

```
この計画で修正を進めてよいですか？
問題なければサブエージェントに実装を委譲します。
```

- ユーザーが承認 → Step 4 へ進む
- ユーザーが修正を求める → 計画を修正して再提示する
- ユーザーが「そのまま進めて」「yes」「ok」などと回答 → Step 4 へ進む

---

## Step 4: サブエージェントへの実装委譲

ユーザーの承認を得たら、**実装用サブエージェント**（Sonnet）を起動して修正計画を渡す。
自分（メインエージェント）でコードを書くのではなく、必ずサブエージェントに委譲する。

### サブエージェントへのプロンプト構成

```
以下の修正計画に従って、コードを修正してください。

## タスクの背景
<ユーザーが報告した問題の説明>

## 修正計画
<Step 2 で立案した修正計画をそのまま貼り付ける>

## プロジェクト情報
- 作業ディレクトリ: <絶対パス>
- 言語・フレームワーク: <プロジェクトの技術スタック>
- テスト実行コマンド: <テストを実行するコマンド>

## 実施してほしいこと
1. 修正計画の各ステップを順番に実施してください
2. 各ファイルを修正する前に必ず現在のコードを Read で確認してください
3. 修正後に「確認方法」に記載したコマンドを実行して動作を確認してください
4. テストが失敗している場合は原因を特定して修正してください

## 制約
- 修正計画に記載されていない変更は原則として行わないでください
- 計画外の問題を発見した場合は修正せず、報告してください
- リファクタリングや機能追加は今回のスコープ外です
```

### モデルの選択

| 修正の複雑さ | モデル |
|------------|--------|
| 単純な修正（1〜2ファイル、原因が明確） | **Sonnet** |
| 複雑な修正（複数ファイル、根本原因の調査が必要） | **Sonnet**（計画は十分練っているため） |

---

## Step 5: 実装結果の確認

サブエージェントが完了したら、メインエージェントが結果を確認する。

**確認すること**:
- 修正計画のすべてのステップが実施されたか
- テストがパスしているか
- 計画外の変更が行われていないか

**結果のユーザーへの報告**:
```
## 修正完了

**修正したファイル**:
- `path/to/file.py` — <変更内容の概要>

**確認結果**:
- テスト: <パス / 失敗の状況>
- 動作確認: <確認できた内容>

**補足**（ある場合のみ）:
- <サブエージェントが発見した計画外の問題や気づき>
```

---

## 注意点

### 計画なしに実装しない

どんなに小さな修正でも、まず計画を出力する。
「1行直すだけ」であっても、計画フォーマットで簡潔に出力してユーザーに確認を取る。

### 根本原因を特定してから計画を立てる

症状だけを見て修正すると、本当の原因を見逃すことがある。
コードを実際に読んでから計画を立てること。

### サブエージェントへの指示は具体的に

「修正してください」だけでは不十分。修正計画を渡すことで、スコープ外の変更を防ぎ、
実装の一貫性を保てる。

### プロジェクトの規約に従う

テストの書き方、命名規則、ファイル構成など、既存コードのスタイルを優先する。
